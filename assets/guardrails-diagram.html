Guardrails — deterministic code around a probabilistic core
Hard rules deterministic. Soft quality may use a model. Never a model for safety.
Input filter
injection · length · allowlist
→
Model
probabilistic core
→
Output filter
PII · schema · policy
→
Final response
safe, scrubbed
Fallback path — never just reject: safe refusal · retry · human escalation
The hidden risk: over-blocking kills adoption faster than under-blocking kills trust. A user wrongly refused three times leaves. Track your false-positive rate, not just your catch rate. Above ~2%, the guardrail costs more than it protects.

✅ Use guardrails when

  • Output is user-facing
  • Actions have consequences
  • Compliance applies (PII, medical, legal)
  • Injection is possible
  • Brand risk exists

❌ Don't rely on them when

  • Output never leaves your system
  • Filtering with another model for hard rules
  • It blocks legitimate work
  • There's no fallback path
  • The rule can't be expressed precisely
  • Guarding only the output

🛡️ The layering principle — never trust one layer

Layer 1 — Input validation      (deterministic, always on)
Layer 2 — Prompt hardening      (instructions, best-effort)
Layer 3 — Output schema check   (deterministic, always on)
Layer 4 — Content policy        (deterministic + model judge)
Layer 5 — Human escalation      (edge cases only)

false_positive_rate = wrongly_blocked / total_legitimate_requests
Target: below ~2%
