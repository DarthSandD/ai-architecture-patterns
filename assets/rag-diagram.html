RAG — Retrieval-Augmented Generation
Search first, then generate. Most RAG bugs are indexing bugs, not model bugs.
Phase 1 — Index (offline, runs once)
Documents
docs · tickets · policies
→
Chunk

→
Embed

→
Vector DB

Phase 2 — Query (per request)
Question
user query
→
Embed
query → vector
→
Search
top-k chunks
→
Guardrail
score < 0.15 → miss
→
LLM
grounded answer
The hidden risk: a retrieval miss gives the model plausible-but-wrong context — and it will use it confidently. Bad retrieval is more dangerous than no retrieval. Always add a score guardrail.

✅ Use RAG when

  • Knowledge changes (docs, tickets, inventory)
  • You need citations
  • Data is private / never trained on
  • Corpus exceeds context window
  • Freshness matters

❌ Don't use RAG when

  • Answer is small & static → just prompt it
  • Model already knows it → wasted latency
  • Need reasoning over ALL data → use code
  • One doc under 5k tokens → paste it whole
  • You can't measure recall → flying blind
